## 一、总体结论

项目定位清晰、文档完整度远高于同阶段开源项目，"没有真机证据就不标记通过"的原则执行得很好。自动化检查全部通过（见附录 A）。

但本次审查发现：**自动化测试只覆盖 `app-utils.mjs` / `motion.mjs` 的纯函数，而 `main.ts`（953 行，承载全部运行时逻辑）没有任何测试**，本次发现的正确性缺陷全部集中在这里。其中有几项与 `PROJECT_STATUS.md` 中标为"已完成"的功能直接矛盾：

| 文档声称已完成 | 实际情况 | 依据 |
|---|---|---|
| "人脸丢失回正" | 人脸丢失或关闭摄像头后，头部保持最后姿态，不回正 | 静态分析，确定 |
| "眼神"驱动 | 对骨骼型 LookAt 模型（VRoid 默认导出）无效，模型医生却显示"眼神可用" | 对照 three-vrm 3.5.5 源码确认 |
| "贴图尺寸和显存估算" | 对 MToon 材质（几乎所有 VRM）贴图计数为 0，显存估算为 0 MB | 在本机用 three-vrm 实测确认 |

另外有两个面向目标用户（中文零基础用户）的**阻断级**问题：

1. 首次构建必须从 `storage.googleapis.com` 下载模型，中国大陆网络环境下大概率失败，整个启动流程中断。
2. README/教程中推荐的"OBS 浏览器来源"路径所依赖的两个前提（与系统浏览器共享模型存储、在"交互"窗口授权摄像头）很可能不成立。

**从“零基础、开箱即用”的目标看**（详见第六节）：核心动捕链路已经跑通，但“开箱”的外壳基本还没有。目前小白要装 Node.js、下载源码、构建；打开后看到的是空白舞台；导入角色后角色是**张开双臂的 T 字形站姿**，没有待机动作；接入直播只考虑了 OBS，而国内很多小白用的是直播姬、直播伴侣或会议软件。第六节列出了按“小白能否用起来”分级的完整未完成功能清单，第七节据此调整了路线顺序：**先让小白能用，再加追踪能力**。

**建议：Gate A 真机验收之前，先完成本报告"阶段 0"的代码与文档整改**，否则真机验收会把已知缺陷当成新问题再发现一遍，浪费稀缺的真机与志愿者时间。

## 三、问题清单

### P0：阻断目标用户的首次使用

#### P0-1 首次构建依赖 Google 存储，中国大陆网络下无法启动 【静态分析 + 需真机】

- **位置**：`scripts/prepare-mediapipe.mjs:8`、`package.json`（`pretest`/`build`）、`start-windows.bat:16-17`
- **现象**：`start-windows.bat` → `npm run build` → `pretest` → `prepare:assets` 从 `https://storage.googleapis.com/...face_landmarker.task` 下载模型。该域名在中国大陆通常不可达；Node 的 `fetch` 也不读取系统代理设置。下载失败时 `npm run build` 报错，启动器停止。`npm ci` 访问 `registry.npmjs.org` 在国内同样慢或不稳定。
- **影响**：产品的第一目标用户是"中文零基础用户"，他们大多会卡在第一步，并且看到的是英文报错。
- **整改建议**（按优先级）：
  1. **发布预构建运行包**：由 CI 在 Windows runner 上构建 `dist/`，连同一个极简静态服务器打包成 zip 附在 GitHub Release（或者先作为 CI artifact）。用户不再需要 `npm ci` 和构建，这也是 v0.3 Tauri 包之前最便宜的"免构建"方案。
  2. 预处理脚本支持镜像地址：新增环境变量（如 `MIAO_FACE_MODEL_URL`），SHA-256 校验不变，因此换源不影响完整性。
  3. 可以考虑把 `face_landmarker.task`（约 3.6 MB，Apache-2.0）直接提交到仓库（需要在 THIRD_PARTY_NOTICES 中附上许可证），彻底去掉构建期下载。
  4. 下载加超时和一次重试，失败时输出中文说明（写明是哪个文件、为什么需要、怎么手动放置）。
  5. 教程中补充 npm 镜像说明（例如 `npm config set registry https://registry.npmmirror.com`），并说明 lockfile 里的地址不受影响。
- **验证**：断开对 googleapis 的访问后，`start-windows.bat` 仍能完成；或 Release zip 在干净 Windows 上无需 Node.js 即可运行。

#### P0-2 OBS 浏览器来源方案的前提很可能不成立 【需真机，高置信】

- **位置**：`README.md` "OBS 使用"一节、`docs/BEGINNER_GUIDE.md` 第 7 节"方法 A"、`main.ts:941-948`
- **现象**：
  1. 文档写"在普通页面先导入一次模型……OBS 页面可自动恢复"。但 OBS 浏览器来源运行在 OBS 自带的 CEF 中，使用独立的存储配置，**与用户的 Edge/Chrome 不共享 IndexedDB**。用户在 Edge 中导入的模型，OBS 页面读不到，结果是透明空白画面。另外 `npm run dev`（5173 端口）和 `npm run start`（4173 端口）属于不同源，存储也互不共享。
  2. 文档写"在 OBS 的交互窗口允许摄像头权限"。据 obs-browser 的已知行为，CEF 浏览器来源不会弹出摄像头授权提示，通常需要用 `--enable-media-stream` 启动参数启动 OBS 才能调用 `getUserMedia`。
  3. 普通页面和 OBS 页面同时打开摄像头时，部分 Windows 摄像头驱动会以"占用"拒绝第二个请求。
- **影响**：按官方教程操作的用户会遇到"OBS 里一片空白"，而且没有任何提示（见 P2-11）。这与项目"第一次使用成功率高"的核心差异化目标相冲突。
- **整改建议**：
  1. **立即修正文档**：在方案可靠之前，把"绿幕 + 窗口捕获"写成推荐路径，浏览器来源改为"进阶/实验"，并写清 `--enable-media-stream`、需要在 OBS 交互窗口内导入一次模型、不要同时打开两个页面的摄像头这三点。
  2. 广播模式在没有模型时显示可交互的"选择 VRM"入口（配合 OBS 的"交互"窗口使用），导入后自动隐藏。
  3. 真机验收时把"OBS CEF 能否恢复模型 / 能否取得摄像头"列为 Gate A 的明确检查项，结论写入文档。
- **验证**：在 OBS 30.x/31.x 中按新教程从零操作，记录结果。

### P1：功能正确性、隐私相关缺陷

#### P1-3 人脸丢失或关闭摄像头后，头部不回正 【静态分析】

- **位置**：`src/main.ts:566`（只在检测到人脸时更新 `latestHead`）、`611-621`（头部目标由 `latestHead - neutralHead` 计算）、`918-925`（人脸丢失只重置 `targetMotion`）、`485-500`（`stopCamera` 不重置头部）
- **现象**：人脸离开画面超过 500 ms 或摄像头关闭后，表情会平滑归零，但 `latestHead` 保留最后一帧的值，头部会一直停在最后的转头或歪头姿态。
- **影响**：直接违反 ACCEPTANCE P0"人脸离开画面后角色平滑回正"；`PROJECT_STATUS.md` 却把它列为已完成。
- **整改建议**：人脸丢失和 `stopCamera` 时执行 `latestHead.copy(neutralHead)`，或者单独维护一个 `headOffsetTarget`，丢失时置为零；让现有的 `slerp` 负责平滑回正。
- **验证**：把头部偏移计算抽成纯函数（输入 latest/neutral/sensitivity/faceVisible，输出目标四元数）并加单元测试；真机验收时专门检查这一项。

#### P1-4 视线驱动对骨骼型 LookAt 模型无效，模型医生误报"眼神可用" 【已验证：对照 three-vrm 源码】

- **位置**：`src/main.ts:374`（`hasLook = Boolean(vrm.lookAt || …)`）、`605-608`（只调用 `setExpression(LookUp/Down/Left/Right)`）
- **现象**：VRM 的 LookAt 分为"表情型"和"骨骼型"两种，VRoid Studio 默认导出骨骼型。骨骼型模型需要设置 `vrm.lookAt.yaw` / `pitch`，由 `VRMLookAtBoneApplier` 转动眼球骨骼；只设置 look 表情没有效果。只要 `vrm.lookAt` 存在，医生就报告"眼神可用"。
- **影响**：最主流的 VRoid 模型眼神不动，诊断却显示正常，用户无从排查。
- **整改建议**：把 `lookLeft - lookRight`、`lookUp - lookDown` 换算成角度，写入 `vrm.lookAt.yaw` / `pitch`（单位是度，量程参考模型 `rangeMap`），两种 applier 都能正确生效；同时移除直接设置 look 表情的代码，避免与表情型 applier 互相覆盖。医生检查改为区分"骨骼型 / 表情型 / 无"。
- **验证**：用一个 VRoid 导出的 VRM 1.0 模型在浏览器中确认眼球随视线转动（可以先在无摄像头时手动设置 yaw 来检查）。

#### P1-5 模型医生漏计 MToon 贴图和 morph target，性能诊断基本失效 【已验证：实测】

- **位置**：`src/main.ts:343-345`、`349-353`
- **现象**：
  1. 代码用 `Object.values(material)` 查找贴图。`MToonMaterial`（three-vrm）的 `map`、`shadeMultiplyTexture` 等是**原型上的 getter**，实际值存放在 `material.uniforms` 中。本次实测：给 MToon 设置两张贴图后，`Object.values` 找到 **0 张**，`uniforms` 中能找到 2 张。因此绝大多数 VRM 会显示"贴图 0 张 · 最大 未知 px · 贴图约 0 MB"。
  2. 几何内存只统计 `geometry.attributes`，没有统计 `geometry.morphAttributes`。VRM 面部通常有几十个 BlendShape，这部分往往是几何内存的大头。
- **影响**：贴图和显存两项风险分级长期显示"正常"，"性能优先"建议永远不会因贴图触发，与文档描述不符。
- **整改建议**：遍历 `material.uniforms` 中 `value.isTexture` 的项，并与自有属性合并去重；几何内存加上 `morphAttributes` 各数组的 `byteLength`。把 `collectModelMetrics` 移入可测试模块，three.js 可以直接在 Node 中运行，可以用合成的 MToon 材质写单元测试。
- **验证**：新增单元测试（MToon + 2 张贴图 → textures=2；带 morph 的几何 → 字节数包含 morph）。

#### P1-6 摄像头启动可重入，导致视频流泄漏、摄像头灯无法熄灭 【静态分析】

- **位置**：`src/main.ts:508-509`（只禁用主界面按钮）、`842-845`（引导弹窗中的摄像头按钮未禁用）
- **现象**：`startCamera` 等待权限或加载引擎期间 `cameraStream` 仍是 `null`，这时再点一次引导弹窗里的"开启摄像头"，会发起第二次 `getUserMedia`。第一个流被第二个覆盖，永远不会被 `stop()`，点"关闭摄像头"后指示灯依然亮着。
- **影响**：与 ACCEPTANCE P0"关闭摄像头后隐私指示 1 秒内熄灭"相冲突，属于隐私敏感问题。
- **整改建议**：增加模块级 `cameraStarting` 标志或 Promise，`startCamera` 进入时直接返回；`updateOnboarding` 中同步禁用 `onboardingCameraButton`。
- **验证**：连续快速点击两个按钮后关闭，确认 `MediaStreamTrack` 全部处于 `ended`（可以用 Playwright 加伪摄像头自动化，见阶段 2）。

#### P1-7 模型加载存在竞态 【静态分析】

- **位置**：`src/main.ts:394-442`、`941`
- **现象**：`loadVrm` 没有加载序号保护。启动时 `restoreModel()` 正在解析一个大模型，用户此时导入新模型；如果新模型先解析完，旧模型随后完成，会把画面替换回旧模型，而 IndexedDB 中存的是新模型。连续拖入两个文件也有同样问题。
- **整改建议**：维护 `loadGeneration` 计数，加载完成时若不是最新一次，就对该次结果执行 `deepDispose` 并丢弃；加载期间禁用导入按钮，或显示"正在加载"。
- **验证**：抽出加载协调逻辑做单元测试，或在 E2E 中模拟。

#### P1-8 `start-windows.bat` 是 LF 行尾，且仓库没有 `.gitattributes` 【已验证】

- **位置**：`start-windows.bat`（`file` 命令确认没有 CRLF）、仓库根目录
- **现象**：教程要求用户"Download ZIP"。ZIP 中的 .bat 保留 LF 行尾。cmd.exe 解析 LF 批处理时存在已知的 `goto`/标签定位异常，在跨 512 字节边界时尤为明显；本脚本依赖 `goto :error` 和 `:server_error`。
- **整改建议**：新增 `.gitattributes`，写入 `*.bat text eol=crlf`（`git archive` / GitHub ZIP 会按该属性转换）；`tests/launcher.test.mjs` 增加"必须是 CRLF"的断言。
- **验证**：Windows 上从 ZIP 解压运行，故意制造错误，确认能跳转到中文或英文错误提示并 `pause`。

### P2：稳健性、体验和一致性

#### P2-9 镜像约定不统一，校准用欧拉角分量相减 【静态分析 + 需真机】

- **位置**：`src/main.ts:549-556`（yaw、pitch 取反，roll 不取反）、`597-598`（左右眨眼直接映射）、`motion.mjs:178-179`（视线左右）、`style.css:207`（预览画面 `scaleX(-1)`）
- **问题**：头部是否镜像、左右眼和视线是否镜像，没有一个统一的开关或约定。代码中头部做了部分取反，眨眼和视线没有做，最终效果可能是"转头像照镜子，眨眼却不像"。校准时用 `latestHead.x - neutralHead.x` 按分量相减，偏离正面较大时（例如校准时本身略微歪头）会产生轴间耦合误差。
- **建议**：定义单一的"镜像模式"设置（默认开启），集中处理头部 yaw/roll、左右眨眼、左右视线；校准改为四元数相对旋转：`offset = inverse(neutralQ) * currentQ`，再按轴限幅。需要真机确认方向后把约定写入 `architecture.md`。

#### P2-10 启动器每次启动都跑完整测试和构建 【静态分析】

- **位置**：`start-windows.bat:16-17`、`package.json:11`
- **问题**：`npm run build` = `npm test && tsc && vite build`。普通用户**每次**双击都要执行完整的测试和类型检查，速度慢，而且任何一个测试失败都会导致无法启动。`npm ci` 只在 `node_modules\.package-lock.json` 不存在时执行，更新代码后依赖不会同步。`node -p` 失败时 `NODE_MAJOR` 为空，`if %NODE_MAJOR% LSS 22` 会产生语法错误。所有提示都是英文。
- **建议**：新增 `build:app`（只执行 prepare 和 vite build），启动器只在 `dist` 不存在或版本变化时构建；比较 lockfile 哈希决定是否重新 `npm ci`；给 `NODE_MAJOR` 设默认值；提示改为中文（文件保存为 UTF-8 并加 `chcp 65001`，或提供中英双语）。有了 P0-1 的预构建包之后，这个脚本只保留给开发者使用。

#### P2-11 广播模式失败时没有任何可见反馈 【静态分析】

- **位置**：`src/main.ts:941-948`
- **问题**：`?broadcast=1` 页面没有模型、摄像头失败或引擎加载失败时，界面全部隐藏，OBS 中只有透明或空白画面，用户无法判断原因。
- **建议**：广播模式增加一个"状态浮层"：出错时显示中文原因和下一步操作，一切正常后自动隐藏；也可以只在 OBS 交互窗口可见（例如鼠标悬停时出现）。

#### P2-12 窗口捕获后备方案存在浏览器节流风险 【需真机】

- **问题**：Chromium 在 Windows 上会对被完全遮挡或最小化的窗口暂停 `requestAnimationFrame`。本项目的推理和渲染都挂在 rAF 上，窗口被遮挡后角色会冻结，OBS 窗口捕获到的是静止画面。
- **建议**：真机确认后在教程中写明"直播窗口不要最小化、不要被完全遮挡"，必要时给出浏览器参数（如禁用后台节流和遮挡检测）的说明。Tauri 版要把这一点列为技术验证项。

#### P2-14 CI 覆盖不足 【已验证】

- **位置**：`.github/workflows/ci.yml`
- **问题**：只有 `ubuntu-latest`，而产品和启动器面向 Windows；每次 CI 都从 Google 下载模型且没有缓存，外部服务波动会导致 CI 变红；没有任何浏览器级测试；`main.ts` 没有测试覆盖。
- **建议**：给 `public/mediapipe` 加 `actions/cache`，key 使用 SHA-256；增加 `windows-latest` job（至少执行构建，并检查 .bat 的 CRLF）；引入最小 Playwright 冒烟测试（见阶段 2）；Windows job 产出 `dist` zip 作为 artifact（对应 P0-1）。

#### P2-15 测试组织和类型声明 【已验证】

- 每个测试文件只用顶层 `assert`，Node test runner 只统计为 5 个测试；第一个断言失败就会掩盖后面的全部检查。建议改用 `test()` / `describe()` 拆分用例。
- `src/*.d.mts` 是手写声明，`tsconfig.json` 只 `include: ["src"]`，不检查 `.mjs` 的实现，声明与实现可能悄悄漂移。建议对 `.mjs` 开启 `checkJs` 并使用 JSDoc，或直接改为 `.ts`，让测试通过 Vite/tsx 运行。

#### P2-16 诊断报告脱敏覆盖不全 【静态分析】

- **位置**：`src/app-utils.mjs:146-153`
- **问题**：没有覆盖 `C:/Users/...`（正斜杠 Windows 路径，WebGL 和部分库的报错中常见）、UNC 路径 `\\server\share\...`、`/mnt/c/Users/...`、macOS `/Volumes/...`。
- **建议**：补充上述正则并加测试用例；另外可以考虑对诊断中的 `userAgent` 做粗化（保留浏览器大版本即可）。

## 六、未完成功能清单（按“零基础、开箱即用”标准）

### 6.1 “开箱即用”的判定标准

本节不按“代码里有没有”来判断，而是站在**一个从没接触过 VTuber、不会命令行、电脑上只有浏览器和直播软件的用户**的角度，看他能不能顺利走完下面这条路径：

> 下载一个文件 → 双击运行 → 马上看到一个会动的角色 → 对着摄像头动一动，角色跟着动 → 放进自己常用的直播或会议软件 → 下次打开还是原样

对照这条路径，当前 v0.2.1 候选版的完成度如下：

| 环节 | 小白期望 | 当前状态 | 结论 |
|---|---|---|---|
| 获取 | 下载一个安装包或压缩包 | 需要装 Node.js、下载源码 ZIP、首次构建联网（国内多半失败） | ❌ 未达到 |
| 启动 | 双击就能打开，不出现吓人的提示 | 黑色命令行窗口、英文提示；每次都跑测试和构建；不能关掉服务器窗口 | ❌ 未达到 |
| 第一眼 | 马上看到一个角色 | 空白舞台，必须先自己准备 VRM | ❌ 未达到 |
| 角色姿态 | 自然站立、会呼吸、会眨眼 | **导入后是 T 字形张开双臂**（VRM 标准的绑定姿势，代码里没有放下手臂）；没有待机动作 | ❌ 未达到 |
| 动起来 | 转头、眨眼、说话都对 | 头部、眨眼、嘴型已实现；眼神对 VRoid 模型无效；丢脸后不回正；左右镜像未确认 | ⚠️ 部分 |
| 放进直播 | 在我用的软件里看到角色 | 只考虑了 OBS；浏览器来源方案前提可能不成立；绿幕要手动加色度键 | ⚠️ 部分 |
| 下次打开 | 角色和设置都还在 | 浏览器内能恢复最后一个模型；换端口或换浏览器就没了 | ⚠️ 部分 |
| 出问题 | 看得懂，知道怎么办 | 中文错误提示和诊断报告做得好；但教程链接到 GitHub（国内慢），反馈渠道只有 GitHub Issue | ⚠️ 部分 |

结论：**核心动捕链路已经跑通，但“开箱即用”的外壳基本还没有**。真正拦住小白的不是动捕精度，而是获取、启动、第一眼和接入直播这几个环节。

### 6.3 “开箱即用”最小集合（建议作为独立里程碑）

**成功标准**（沿用 `PROJECT_PLAN.md` 第 15 节的思路，但改为可执行的测试）：找 5–10 名从未接触过 VTuber 的用户，只给他们一个下载链接，不做任何口头指导，记录两个指标：

- 20 分钟内出现在自己常用的直播或会议软件里的比例

两个指标都达到 80% 时，才算“开箱即用”。

### 阶段 5：v0.4「直播可用性」（建议与原 v0.4 身体追踪对调）

- 虚拟摄像头输出（先做技术验证）、透明窗口输出
- 开播前 60 秒检查、横屏/竖屏输出比例
- 命名配置档、表情热键

**调整理由**：单摄像头身体追踪抖动风险高、对低配电脑不友好，对小白的价值低于“能稳定出现在自己的直播软件里”和“没有摄像头也能用”。身体追踪作为高风险技术项，放到直播可用性稳定之后，也符合计划书“一个里程碑只允许一个高风险技术项”的原则。

### 阶段 6：v0.5「身体与进阶输出」→ v0.9 RC → v1.0

- v0.9 RC：跨崩溃日志、自动更新、依赖与许可证审计、P0 功能冻结
