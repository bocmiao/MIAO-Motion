## 一、结论

Codex 这一轮进展很大，新增并发布了以下能力：

- 原创猫角色"喵小动"
- 换色
- 表情热键
- 麦克风嘴型
- 自动画质
- 更新检查
- 身体/手部识别
- OBS 自动配置
- 手机面捕
- **原生虚拟摄像头**

v0.3.0-beta 已公开发布，安装包和便携包的校验值与发布记录一致。

**主链路是通的**：打开程序 → 选"喵小动" → 进入绿幕直播画面 → 窗口捕获，全程正常，首次打开也不会访问外网。

但是"全部完成"**不成立**。新增功能里有 **4 项直接失效**：

- 手机面捕：眨眼、微笑、视线都收不到；
- 手指追踪：永远不动；
- VRM 0.x 模型的身体追踪：四肢方向错；
- 身体追踪的镜像：左右反了。

另外，安装版的虚拟摄像头存在**卸载后残留"幽灵摄像头"**和**提权安全隐患**。这些问题之所以没被测出来，是因为对应的测试用了伪造数据，或者只检查了文案（见第四节）。

## 三、问题清单

### P1：功能失效或安全问题

**① 手机面捕只剩张嘴，眨眼、微笑、视线全部收不到【实测 + 源码】**

- **位置**：`src/phone.ts:9`
- **原因**：解析规则 `/^([a-zA-Z]{2,40})-(...)$/` 不接受下划线。而 iFacialMocap 官方格式的表情名带下划线，例如 `eyeBlink_L`、`mouthSmile_R`。即使放开下划线，这些名字也和动作求解器使用的 `eyeBlinkLeft` 对不上。
- **测试漏洞**：测试 `tests/e2e/studio.spec.mjs:163` 伪造的数据包是 `eyeBlinkLeft-20`，并非真实格式，所以测不出来。
- **整改**：
  - 规则允许 `_`，并把 `_L/_R` 映射为 `Left/Right`；
  - 核对 ARKit 与 MediaPipe 的左右约定是否需要互换；
  - 测试改用按官方规格构造的完整数据包，并断言眨眼、微笑确实生效。

**② 手指永远不动【实测】**

- **位置**：`src/body-tracking.ts:44`
- **原因**：tasks-vision 1.0.1 的手部关键点 `visibility` 恒为 0。门控条件 `(visibility ?? 1) < 0.5` 因此把所有手指旋转都挡掉了。
- **整改**：手部点改用 handedness 置信度作为门控条件；测试要断言手指骨骼角度确实发生变化。

**③ VRM 0.x 模型的身体追踪四肢方向错误【实测】**

- **位置**：`src/body-tracking.ts:54`
- **原因**：父骨骼的世界旋转里已经包含 `rotateVRM0` 的翻转，这一行又手动翻了一次 x/z，等于翻转了两次。
- **后果**：侧平举时手臂横穿身体，前伸变成向后，脚尖也朝后。VRM 1.0 模型（猫、pixiv 示例）不受影响。
- **整改**：删除第 54 行；增加一个 VRM 0.x 夹具，断言"侧平举时手在身体外侧"。

**④ 身体追踪的镜像是反的【实测，用合成关键点】**

- **位置**：`src/body-tracking.ts:51、71、84`
- **现象**：默认开启镜像时，用户举右臂，角色举的却是屏幕左侧那只手，与镜像预览画面相反；关闭镜像时反而表现得像镜像。脸部追踪的镜像约定是正确的，两者不一致。
- **整改**：`xSign`、身体左右对应、手部左右标签三处同时取反，并与脸部约定写成同一个纯函数，统一测试。

**⑤ 身体追踪在主线程同步推理，帧率减半【实测】**

- **现象**：单次身体推理约 33 ms，手部约 105 ms，每 100 ms 触发一次。开启后帧率从 7.1 降到 3.4（软件渲染，数值偏低，但减半的比例有参考意义），最差单帧 401 ms。
- **连锁问题**：自动画质把 CPU 瓶颈误判为渲染瓶颈，把清晰度一路降到 0.5，画面变糊却没有任何收益。
- **整改**：
  - 推理放进 Worker；或者身体和手部隔帧交替，只在手腕可见时才跑手部识别；
  - 自动画质只在渲染耗时是瓶颈时才降清晰度。

**⑥ 卸载喵动不会注销虚拟摄像头，留下"幽灵摄像头"【源码，已本人核实】**

- **位置**：`src-tauri/tauri.conf.json` 的 NSIS 配置里没有卸载钩子
- **现象**：注册信息写在系统级注册表。小白直接卸载喵动后，所有会议软件里仍然会列出 "MIAO Motion Camera"，一选就报错。此时 DLL 已经删除，没法再手动清理，只能重装喵动，再点"卸载组件"。
- **整改**：增加 `NSIS_HOOK_PREUNINSTALL`，卸载前以管理员身份调用 `camera-register.exe unregister`；CI 增加"注册状态下卸载 → 设备消失"的测试。

**⑦ 管理员注册的是用户可写目录里的 DLL，存在提权风险【源码】**

- **原因**：安装器默认是"当前用户"模式，程序装在用户可写目录；注册程序却以管理员身份，把该目录下的 `softcam.dll` 注册成全局摄像头。
- **风险**：
  - 之后任何普通权限进程都可以替换这个 DLL，所有以管理员身份运行、会枚举摄像头的程序（例如管理员模式的 OBS）都会加载它；
  - 同一台电脑上的其他 Windows 账户也能看到这个设备，但用不了；
  - 没有管理员密码的学校或公司电脑完全无法使用。
- **整改**：注册前把 DLL 复制到 `Program Files` 下的受保护目录再注册（顺带解决 ⑥），或者把安装器改为"所有用户"模式。

**⑧ 虚拟摄像头只有 64 位，32 位会议软件可能看不到【需真机】**

- **背景**：部分腾讯会议、钉钉、企业微信版本可能是 32 位，需要在真机任务管理器的"平台"列确认。
- **整改**：softcam 支持 32 位和 64 位共享同一块内存，多编译一个 32 位 DLL 并用 SysWOW64 下的注册程序注册即可，成本较低。

**⑨ 验证结论有夸大，测试有假覆盖【源码】**

- 原生摄像头：CI 验证的是独立测试程序（`smoke-sender.cpp`）发出的四色测试图，注册方式是 `regsvr32`。"应用画面 → Tauri → 虚拟摄像头"这条真实链路，以及 UAC 注册程序，都没有端到端验证。但 `PROJECT_STATUS.md:14` 写"实际输出角色帧"，`CHANGELOG.md:10` 写"实际收帧验证"，`README.md:18` 直接写"支持"，都没有标注"实验"。
- 身体追踪测试（`studio.spec.mjs:119`）：断言 `/身体.*手部/`，而初始文案"身体和手部追踪未开启"本身就能匹配。引擎从没启动也会通过，也完全没有检查骨骼是否动了。
- 手机面捕测试：用的是伪造格式，见 ①。
- 猫角色测试：只截图，没有断言颜色或表情是否真的生效。
- **整改**：
  - 夸大的表述改为"实验功能，应用内链路待真机验证"；
  - 身体测试改为断言状态变为"已开启"并且骨骼角度变化；
  - 新增"应用画布 → 桥接 → 发送端"的帧内容断言。

**⑩ 文档过时、互相矛盾【源码】**

- `BEGINNER_GUIDE.md:55` 仍写"不内置捏人"，没提喵小动；`:163-164` 仍写"不支持身体、麦克风嘴型、原生虚拟摄像头"。
- `LIVE_PLATFORM_GUIDE.md:59` 写"当前没有原生虚拟摄像头"，与同文件 `:66-68` 自相矛盾。
- `README.md:29`、`BEGINNER_GUIDE.md:19` 推荐便携版，`download.html` 推荐安装版；而便携版没有虚拟摄像头和手机面捕，下载页没有说明这一点。
- 安装版是桌面窗口，但多处文档仍写"选择浏览器窗口"（`help.html:32`、`BEGINNER_GUIDE.md:114`、`LIVE_PLATFORM_GUIDE.md:12`）。
